## What this is

**AIMS** (Asset/Infrastructure Management System) — branded **SIMS** (Structural Integrity Management System) in the UI — a .NET 10 Clean Architecture web app for Badak LNG (Bontang, Indonesia) to track structural/civil assets (tanks, foundations, pipelines, etc.) across plants, with condition inspection (Good/Fair/Poor), GIS mapping, and audit trail. Razor Pages + Dapper (no EF Core), Autofac-hosted DI (properly wired 2026-07-14 via `builder.Host.UseServiceProviderFactory` — the original wiring built a container and discarded it, so the app silently ran on MS DI), dual SQL Server/Oracle support.

`docs/PROJECT_STUDY.md`-style deep dive lives in `PROJECT_STUDY.md` at the repo root — read it for exhaustive entity/service/page tables. **It is dated 2026-06-29 and predates the Plant-entity refactor, the `LookupCodes.cs` lookup tables, and the `Condition`/legacy-field cleanup described below** — trust the current code over that file for `AssetItem`/`Plant` shape. `WORK-SUMMARY-*.md` files log day-by-day changes chronologically and are more current.

The `SIMS Dashboard Rev A/B *.pptx` files are the UI design spec (wireframes built as native PowerPoint shapes, not screenshots) that pages under `Pages/AssetItems`, `Pages/Plants`, and `Pages/Index.cshtml` are being built to match. When asked to study or implement against them, extract via `python3 -m zipfile` (no `unzip`/LibreOffice available in this environment) — slide XML text runs (`<a:t>`) give the copy, shape `<a:xfrm>`/`<a:solidFill>` give layout and color, embedded media are photos/charts, not screenshots of the actual UI.

### Production deployment

Two scripts, run in order, share one gitignored `deploy/deploy.conf` (copy from `deploy/deploy.conf.example`):

- `deploy/upload.sh` runs on your **dev machine**. It zips the repo's tracked-ish source (excludes `.git`, `bin`/`obj`, `.vs`, logs, `deploy.conf` itself, and the runtime upload dirs `wwwroot/asset-pictures`/`asset-documents`) with `python3 -m zipfile`/`zipfile` module — not the `zip`/`unzip` CLIs, since neither is guaranteed installed locally or on the server, same reasoning as the `.pptx` extraction note below — then `scp`s it over and extracts it into `REMOTE_DIR` on the server.
- `deploy/deploy.sh` then runs **on the target Ubuntu server itself** (in an SSH session, from that extracted checkout), not from the dev machine: an earlier version tried to publish locally and `rsync`/`ssh` the result over, but password-based SSH in this environment can't satisfy `sudo`'s password prompt through a piped/non-tty connection (rsync's internal `ssh` has no real terminal, and even shipping the provisioning script over `ssh -t` left stdin occupied by the script itself), so running locally on the box sidesteps the whole problem. It deploys `AIMS.WebFrontend` behind nginx (plain HTTP reverse proxy) with Oracle installed locally on that same server, and is idempotent: first run installs the ASP.NET Core runtime, nginx, and a dedicated `aims` system user; every run publishes a new timestamped release directly into `/opt/aims/releases/`, symlinks persistent data (`appsettings.Production.json`, `wwwroot/asset-pictures`, `wwwroot/asset-documents`, `Logs/`) in from `/opt/aims/shared/` so uploads and secrets survive redeploys, flips the `/opt/aims/current` symlink, restarts the `aims-webfrontend` systemd service, reloads nginx, and prunes old releases. Oracle itself is not installed/configured by the script — it's assumed already running on the server at `localhost:1521`; only the connection string in the shared `appsettings.Production.json` needs the real password.

### Database backup/restore

To pull the server's backup files down into the local gitignored `./.db_backups/` folder (run from the repo root):

```bash
scp root@159.223.33.82:/opt/aims/backups/* ./.db_backups/
```

`deploy/db_backup.sh` (`backup` / `restore <file> [--yes]` / `list` subcommands) runs on the same server, reusing `deploy/deploy.conf`. It reads the live Oracle connection string straight out of `$APPSETTINGS_FILE` (default `$BASE_DIR/shared/appsettings.Production.json`, overridable in deploy.conf) and does a schema-level Data Pump export/import (`expdp`/`impdp`) of the app's DB user, writing timestamped `.dmp`/`.log` files to `$BASE_DIR/backups` (pruned to `KEEP_BACKUPS`, default 7). `restore` is destructive (`table_exists_action=replace`) and requires typing `yes` unless `--yes` is passed.

Creating the Data Pump `DIRECTORY` object needs a DBA connection, which the script gets via OS authentication (`sqlplus / as sysdba`) rather than a documented SYS/SYSTEM password — it auto-detects whether Oracle is the `setup_oracle_xe.sh` podman container (by container name, overridable via `ORACLE_CONTAINER_NAME`) and runs everything through `podman exec --user oracle` + `podman cp`, or otherwise assumes a native install and runs as the OS user that owns it (`ORACLE_OS_USER`, default `oracle`) via `sudo -u <user> env ORACLE_HOME=... ORACLE_SID=...` — the env is exported explicitly rather than relying on a login shell/`oraenv`, so the account needs no home directory or profile (fixed 2026-08-17). The DB password is deliberately kept out of any command line (visible via `ps` otherwise) — it only ever goes into a Data Pump parameter file written with tightened permissions and deleted immediately after use.

`deploy/db_backup_sqlplus.sh` (same `backup`/`restore`/`list` subcommands, added 2026-08-17) is the fallback that needs **nothing but a working `sqlplus` and a plain user/password connection string** — no `expdp`/`impdp`, no local Oracle home, no OS auth, no DIRECTORY objects, works against a remote Oracle as long as the connected user owns the schema (it dumps the connected user's own tables). Connection string comes from a positional arg (`backup 'user/pass@//host:port/service'`), `DB_CONNECTION_STRING`, or `$APPSETTINGS_FILE`; sqlplus is auto-discovered (Instant Client dirs are globbed and their `LD_LIBRARY_PATH` exported). `backup` writes one `aims_<stamp>.sql` per run to `$BACKUP_DIR` (schema DDL via `dbms_metadata` — tables+constraints, non-generated indexes, sequences, triggers — plus full data as typed INSERTs: NUMBER/DATE/TIMESTAMP/TZ/CLOB-aware, quote-escaped, `&`-safe, NLS-pinned; parents-before-children via FK ref-count ordering). `restore` drops the connected user's tables (`CASCADE CONSTRAINTS`), replays the file, then re-bumps every sequence above `MAX(Id)` (matched by `<Table>_SEQ` name or by scanning trigger bodies) so the app's `WHEN (new.Id IS NULL)` NEXTVAL triggers can't collide with restored rows. Limits: CLOB/NCLOB ≤ 15,000 chars (backup fails loudly rather than truncate), single-level FK chains only, restore into the same database instance (DDL carries `TABLESPACE "USERS"`). Gotcha that already bit once: every SQL statement in a sqlplus heredoc **must end with `;`** (or `/` for PL/SQL blocks) — an unterminated `ALTER SESSION` merges with the following `SPOOL`/`PROMPT`/`SELECT` lines into one buffer and fails with ORA-02248.

TLS is optional and off by default. `deploy/deploy.sh`'s nginx site is gated by `NGINX_ENABLE_SSL` (default `false`): when false it emits the legacy single plain-HTTP listener on `NGINX_LISTEN_PORT` (prod runs on :81); when true it emits a `:443 ssl` block (using `NGINX_SSL_CERT`/`NGINX_SSL_KEY`) plus a `:80 → :443` 301 redirect block, and forwards `X-Forwarded-Proto=$scheme` so the app knows it's behind HTTPS. `Program.cs` runs `UseForwardedHeaders` (trusting only loopback, so an outside attacker can't spoof `X-Forwarded-Proto`) before `UseHsts` (non-Dev only) and `UseHttpsRedirection`. With no `HttpsRedirection:HttpsPort` configured anywhere in `appsettings*.json`, `UseHttpsRedirection` is a no-op when SSL is off (just logs a warning) and `UseHsts` over plain HTTP is ignored by browsers — so the legacy plain-HTTP prod-on-:81 deploy keeps working unchanged. Don't remove the `UseForwardedHeaders`/`UseHsts`/`UseHttpsRedirection` pipeline without also re-checking the SSL setup, and don't add `HttpsRedirection:HttpsPort` to `appsettings*.json` without `NGINX_ENABLE_SSL=true` on the server (it would 307 browsers to a non-existent :443 and break the plain-HTTP prod).

### Hosting at https://dtp.devtim.my.id (Cloudflare proxy + Origin Cert)

This is the canonical HTTPS deployment for the project — Cloudflare's orange-cloud proxy in front of nginx, with a free Cloudflare Origin Certificate on the server for the CF→origin hop (Full strict mode). No Let's Encrypt/certbot needed. One-time Cloudflare dashboard setup, then a `deploy.conf` flip and `deploy.sh` rerun:

1. **Cloudflare dashboard → SSL/TLS → Origin Server → Create Certificate** — RSA, 15-year validity, hostnames `*.devtim.my.id` and `devtim.my.id`. Copy the cert and key onto the server:
   ```bash
   sudo install -d -m 0755 /etc/ssl/cloudflare
   sudo tee /etc/ssl/cloudflare/dtp.devtim.my.id.pem >/dev/null   # paste cert, Ctrl-D
   sudo tee /etc/ssl/cloudflare/dtp.devtim.my.id.key >/dev/null  # paste key,  Ctrl-D
   sudo chmod 600 /etc/ssl/cloudflare/dtp.devtim.my.id.key
   ```
   (These cert/key paths are the `deploy.sh` defaults — override via `NGINX_SSL_CERT`/`NGINX_SSL_KEY` in `deploy.conf` if you put them elsewhere. Cloudflare Origin Certs are only valid when reached *through* Cloudflare's proxy; if you ever switch the DNS record to grey-cloud/direct, replace them with a public cert like Let's Encrypt.)
2. **Cloudflare DNS** — A record `dtp.devtim.my.id` → your server's public IP, **Proxied** (orange cloud).
3. **Cloudflare SSL/TLS → Overview → Encryption mode = Full (strict)**. This validates the Origin Cert on the CF→origin hop (Step 1) while Cloudflare presents its own browser-trusted cert to visitors.
4. **Cloudflare SSL/TLS → Edge Certificates → Always Use HTTPS = On** (optional but recommended — Cloudflare 301s any `http://` visitor to `https://` at the edge before it ever reaches your server).
5. **`deploy/deploy.conf` on the server** — set the four SSL-related vars (defaults shown):
   ```bash
   SERVER_NAME="dtp.devtim.my.id"
   NGINX_ENABLE_SSL="true"
   NGINX_SSL_CERT="/etc/ssl/cloudflare/dtp.devtim.my.id.pem"
   NGINX_SSL_KEY="/etc/ssl/cloudflare/dtp.devtim.my.id.key"
   NGINX_REDIRECT_HTTP_TO_HTTPS="true"   # emit the :80 → :443 301 block (set false to drop :80 entirely)
   ```
   `SERVER_NAME` must be the real hostname (not `_`) when SSL is on, otherwise nginx won't match `dtp.devtim.my.id` against the `:443` server block.
6. Rerun `./deploy/deploy.sh` — it rewrites the nginx site with the `:443 ssl` + `:80` redirect blocks, opens `443/tcp` (and `80/tcp`) in ufw if active, and runs an extra health check via `curl --resolve dtp.devtim.my.id:443:127.0.0.1 https://...` to confirm the cert + proxy path end-to-end before reporting success.

The existing `appsettings.Production.json` on the server keeps its Oracle/QGIS settings (`QgisServer:MapProject` and `deploy.conf`'s `QGIS_MAP_PROJECT` point at the Sample Citra project since 2026-08-28 — see the QGIS Server section) — no `HttpsRedirection:HttpsPort` is needed for the SSL case, since nginx 301s `:80` before the app sees it and the app only ever receives `https`-scheme requests through `X-Forwarded-Proto`. Oracle itself is unchanged (still assumed running on `localhost:1521` on that same server).

**Logging:** `Program.cs` uses Serilog (`Serilog.AspNetCore`) as the sole logging provider — console plus a rolling file sink — reading sinks/levels from the `Serilog` section of `appsettings*.json` (fixed 2026-07-14: an earlier version of this same change built `Log.Logger` entirely in code and called `builder.Host.UseSerilog()` with no arguments, which silently ignored that JSON section — `ReadFrom.Configuration` is required for it to actually take effect). The plain ASP.NET Core `Logging` section is gone from `appsettings.json`/`appsettings.Development.json` since it's dead once Serilog owns logging — overrides belong under `Serilog:MinimumLevel` instead. The file sink writes to `Logs/aims-.log`, resolved relative to the working directory (the project dir under `dotnet run`; in production, `deploy/deploy.sh` symlinks each release's `Logs/` to a persistent `shared/Logs/` dir — same pattern as `asset-pictures`/`asset-documents` — so history survives redeploys and release pruning). A bootstrap console-only logger covers the window before config loads, including `InitializeDatabase()`'s schema-init pass which runs before `builder.Build()`; `app.UseSerilogRequestLogging()` logs each HTTP request; a top-level `try/catch/finally` around `app.Run()` calls `Log.Fatal`/`Log.CloseAndFlush()` on startup failure so it isn't lost. Don't reach for `Console.WriteLine` for diagnostics — inject `ILogger<T>` instead (see `LoginModel`'s exception handler).

There's no headless browser (no chromium, Playwright is Windows-side Node with WSL path friction) — verify UI changes by rebuilding, running the app, and inspecting HTTP responses/markup, or ask the user to check in a real browser.

**Razor compiler gotcha (this .NET 10 SDK):** a code block whose markup starts on the same line as `{` (e.g. `{ <span>...</span> }`) or has blank lines immediately after `@if (...) {` before the first tag fails to parse — and the failure cascades into unrelated bogus errors elsewhere in the same compilation (unrelated files, "top-level statements" duplication, etc.), making the real cause hard to spot. Always put markup on its own line right after the opening brace. If a build suddenly produces a wall of nonsensical errors across many files, clean `obj`/`bin` for `AIMS.WebFrontend` and look for this pattern first before assuming something else broke.

## Architecture

Dependency direction: `AIMS.WebFrontend → AIMS.Infrastructure → AIMS.Core → AIMS.SharedKernel` (Core has zero infrastructure dependencies).

- **AIMS.SharedKernel** — `BaseEntity`, `ValueObject`, `IRepository`, `IHandle<T>`, `IDomainEventDispatcher`, `IAuditUserProvider`, `IActivityLogger`.
- **AIMS.Core** — domain entities (`Entities/AssetItem.cs` holds `AssetItem`, `Plant`, `AssetItemRemarks`, `AssetItemDocuments`, `DocumentTypeCode`; `AssetItem` has a `Category` field (`string?`, `nvarchar(250)`) added 2026-08-04, displayed as a select dropdown in Create/Edit pages with options "Equipment / Main Structure" and "Foundation / Supporting Structure" — moved to the **Asset Register** section (from Asset Attribute) on 2026-08-04, and shown read-only in the Asset Register table in Details; `Entities/LookupCodes.cs` holds static lookup tables `AssetCode`/`CivilAssetCode`/`PlantCode` used for dropdowns and tag generation — `PlantCode` (added 2026-07-23) maps a fixed Plant `Code` → `Description` reference list, used to render the `Code` field as a select and auto-fill `Description` on the Plants Create/Edit pages; Plants themselves remain a fully DB-backed entity managed via the `/Plants` CRUD pages, not seeded from this static list, since `DatabaseInitializer`/`OracleSchemaInitializer` dropped that seeding step on 2026-07-08), domain events/handlers, `AuditLog`. `AssetItemRemarks`/`AssetItemService.GetRemarksAsync`/`AddRemarkAsync` still exist but are unreachable from the UI since the Condition (GVI) tab's remarks section was removed 2026-07-07 in favor of the picture carousel.
- **AIMS.Infrastructure** — Dapper repositories, the SQL Server/Oracle strategy-pattern abstraction, Dapper-backed ASP.NET Core Identity stores, audit logging, startup extensions (`StartupSetup.cs`), Autofac modules (`DependencyInjection/CalculationsModule.cs`). DI is hybrid: plain `IServiceCollection` registrations in `StartupSetup.cs`/`Program.cs` get `Populate()`d into the Autofac root container (`builder.Host.UseServiceProviderFactory` in `Program.cs`); Autofac-specific wiring (assembly scans, decorators) lives in modules registered via `ConfigureContainer`. The old `ContainerSetup.cs` (which built a container and discarded it) was deleted 2026-07-14 when the hosting was wired properly. Per-AssetCode calculation strategies (`AIMS.Core/Services/Calculations/`): implement `IEquipmentCalculation` in that namespace and the assembly scan registers it automatically; `ConditionAdjustedCalculation` is layered over every strategy via `RegisterDecorator` (keep it excluded from the scan); `IEquipmentCalculationResolver` picks the strategy by `AssetCode` with `DefaultEquipmentCalculation` (empty code) as fallback. Interval values are placeholders pending real engineering numbers. `AssetItemService.DeleteAsync`/`PlantService.DeleteAsync` run their multi-statement deletes (documents/remarks/asset; detach-assets/plant) inside a DB transaction (fixed 2026-07-14 — previously a failure mid-sequence could leave child rows deleted but the parent row intact). `FileUploadHelper.DeleteFile` canonicalizes the target path and refuses to delete anything that resolves outside `wwwroot` (hardened the same day against a path-traversal `../` payload in a stored file path).
- **AIMS.WebFrontend** — Razor Pages UI. There are no EF migrations anywhere; the old empty `AIMS.Migrations.{SqlServer,Oracle,PostgreSQL}` placeholder projects were dropped from the solution and their now-orphaned `bin`/`obj` artifact dirs deleted 2026-07-14 — don't recreate them.

### No EF Core, no migrations — idempotent DDL instead

Schema is created/altered by `ISchemaInitializer` (`DatabaseInitializer.cs` for SQL Server, `OracleSchemaInitializer.cs` for Oracle), run on every app startup via `services.InitializeDatabase()`. All DDL is guarded (`IF OBJECT_ID(...) IS NULL` / Oracle `EXECUTE IMMEDIATE` with `ORA-00955` catch) so re-running is always safe. **Adding a field means adding a guarded `ALTER TABLE` block to both schema initializers**, not writing an EF migration.

One-time data backfills (e.g. seeding `Plants` from the old hardcoded lookup, migrating a legacy `IntegrityStatus` enum into the `Condition` string field, dropping now-unused legacy columns) are also written as idempotent C# migration steps inside these same initializer classes — see `MigrateLegacyIntegrityStatus` / `DropLegacyAssetItemColumns` for the pattern: backfill before drop, and run every boot behind existence checks.

### Oracle compatibility layer

Oracle uses `:Name` bind params while Dapper/SQL Server code is written with `@Name` — `OracleParamConnection`/`OracleParamCommand` rewrite parameters and coerce `DbType.Boolean` to `Int32` transparently. `ISqlDialect` (`SqlServerDialect`/`OracleDialect`) abstracts identifier quoting, insert-and-return-id, and pagination (`OFFSET/FETCH` vs `ROW_NUMBER()`) so `DapperRepository`/service classes stay provider-agnostic.

`OracleParamConnection.BeginDbTransaction` maps `IsolationLevel.Unspecified` (what a parameterless `conn.BeginTransaction()` passes) to `ReadCommitted`, since ODP.NET raises `ORA-50002` on `Unspecified` directly — fixed 2026-07-14 alongside the `AssetItemService`/`PlantService` transactional-delete fix above; before that, no transaction had ever actually been opened successfully through this wrapper. `ISqlDialect.EscapeLike` (added the same day) escapes user-supplied `LIKE` search terms so a literal `%`/`_` in the search box doesn't act as a wildcard — SQL Server's implementation also escapes `[` (its character-class opener), which Oracle's must not do since escaping a non-wildcard character there raises `ORA-01424`. Callers pair it with an explicit `ESCAPE '\'` clause and `UPPER()` on both sides for case-insensitive matching (Oracle's `LIKE` is case-sensitive by default, unlike SQL Server's) — see `AssetItemService.GetPagedAsync`'s search clause and the Audit Logs username filter.

### Asset tagging

`AssetItem.AssetId` (the human-facing tag) is **always computed server-side** via `AssetItem.GenerateAssetId(plantCode, assetCode, civilAssetCode, assetOrder, category)`, called from `AssetItemService.CreateAsync`/`UpdateAsync`. It is never a bound/editable form field — the UI shows a read-only, JS-live-updated preview instead. Keep this generation logic out of any new form input binding.

**Category-based formula (2026-08-04):** The tag format depends on `AssetItem.Category`:
- `"Equipment / Main Structure"` → `{plantCode}{assetCode}-{assetOrder}` (e.g. `17D-1`)
- `"Foundation / Supporting Structure"` → `{plantCode}{civilAssetCode}-{assetOrder}-Q` (e.g. `17D-1-Q`)
- `null`/other → legacy combined format `{plantCode}{assetCode}/{civilAssetCode}-{assetOrder}` (e.g. `17D/4-2`)

The JS preview in `Create.cshtml`/`Edit.cshtml` mirrors this logic client-side, watching `#Input_Category` alongside the other tag fields. The schema initializers' `RegenerateAssetIds` migration also fetches `Category` and passes it through to recompute existing rows on startup.

`Plant.Code` is `int?` (migrated from `string?` on 2026-07-07 — see idempotent `MigratePlantCodeToInt` in both schema initializers for the string→int conversion of existing rows). `AssetItem` has no `QrCode` field — the QR image always encodes `AssetId`, generated on the fly by `Pages/AssetItems/QrCode.cshtml.cs` and surfaced via a "View QR Code" button that opens `PrintTag.cshtml` in a small popup (see `openCenteredPopup()` in `site.js`) rather than a stored URL.

Both `Pages/Index` and `Pages/AssetItems/Index` PageModels inject `IConfiguration` (+ `IHttpClientFactory` on AssetItems) and expose `QgisServerUrl`/`QgisBrowserUrl`/`MapProject`; `?handler=FeatureInfo` is a per-page WMS proxy (`OnGetFeatureInfoAsync` in `MapDemo/Index.cshtml.cs` and `AssetItems/Index.cshtml.cs`, both returning `text/plain`). **Browser-facing URL (`QgisBrowserUrl`, exposed to the JS via `data-qgis-server`/`const QGIS_SERVER`)** is `QgisServer:BrowserUrl` when set, falling back to `QgisServer:ServerUrl` otherwise — so dev (`dotnet run`, no nginx) hits the upstream directly, while prod sets `BrowserUrl=/qgisserver` and `deploy.sh`'s nginx proxies `/qgisserver` → `$QGIS_SERVER_URL` so the browser talks same-origin HTTPS to nginx (which forwards over plain HTTP to the upstream internally). This avoids **mixed-content blocking** — an HTTPS page may not fetch HTTP subresources, so embedding `http://159.223.33.82:8081/qgisserver` directly in the JS of an HTTPS page makes both the GetCapabilities `fetch()` and every Leaflet WMS tile request fail silently in the browser console. Don't point the browser-facing JS at a plain-HTTP URL on the HTTPS deployment; set `QgisServer:BrowserUrl=/qgisserver` (the `deploy.sh` default) and let nginx proxy. The auto-search (`doSearch`) is MapDemo's layer search minus the input UI: the first term substring-matching a layer name wins (case-insensitive, space/underscore-tolerant so `Plant 17` matches `Plant_17`) and runs MapDemo's zoom — **+2 levels at the current center** (explicit user choice over fit-to-extent) then a FeatureInfo popup at center when feature-info is on. Because of that zoom, any page passing `data-search-terms` must also set `data-init-*` to the site view (`0.08744, 117.48562` z16), or the zoom lands on empty map. `AssetItems/Index.cshtml.cs` builds `SearchTermsJson` as asset tag → plant name → plant code; MapDemo's own page is untouched and keeps its search input UI (its hardcoded fallbacks still name the old ortho projects — harmless since config always provides values).

### QGIS Server deployment & the asset point lookup (2026-08-28)

Both QGIS boxes run **QGIS Server 4.2.1 in a podman container** (image `docker.io/qgis/qgis-server:4.2.1-questing`; its internal nginx serves QGIS under the `/ows/` prefix on port 80), because QGIS 4.x desktop saves projects in a format whose WFS publish flags QGIS Server 3.x can't read (see gotcha below). QGIS 4.x apt packages don't exist for Ubuntu 24.04 (noble), only 26.04 (resolute) — hence containers.

- **Dev box 192.168.0.8**: rootless podman as user `deli`, container `qgis-server4` bound to `127.0.0.1:8091`, **user** systemd unit `container-qgis-server4.service` + linger (starts at boot). nginx `/qgisserver` → `proxy_pass http://127.0.0.1:8091/ows/;` with `proxy_set_header Host $host`.
- **Prod 159.223.33.82**: **root** systemd unit `qgis-server4.service`, same image, `-v /home/qgis/projects:/home/qgis/projects:ro`, bound `127.0.0.1:8091`. The nginx **:8081 listener** (`/etc/nginx/sites-available/qgis`) proxies `/qgisserver` → `127.0.0.1:8091/ows/`; the public `aims-webfrontend` proxy (→ `127.0.0.1:8081`) is unchanged.
- **Rollback on both**: the native `qgis-server.service` (3.44.7 / 3.34.4) still runs — revert the one `proxy_pass` line back to `fastcgi_pass unix:/var/run/qgisserver.socket;` and reload nginx.
- **Project locations**: dev `/home/deli/Sample Citra/Project Sample format qgs.qgs`; prod `/home/qgis/projects/SampleCitra/Project Sample format qgs.qgs` (prod `deploy.conf` `QGIS_MAP_PROJECT` + `appsettings.Production.json` `QgisServer:MapProject` point there). **Update workflow: save in QGIS 4 desktop → copy the folder to the server — no conversion step** (servers read the QGIS-4 format natively). Copy the KML files too: the hidden `Site Plan` layer has a folder datasource (`.`) and the whole project 500s with "Layer(s) not valid" if `Identified Asset 20260820.kml`/`Plant 17 (20 ea).kmz` are missing from the project folder (bit us on prod).

**Asset point lookup**: `AssetItems/Index.cshtml.cs` `OnGetAssetPointAsync` resolves the plant group's point layer dynamically — WMS GetCapabilities (static 60s cache) → group matched by plant code token → the group child whose name contains "Point" or geometryType is Point — then WFS `GetFeature` filtered by the asset tag with an OGC XML `FILTER` (`PropertyIsLike` suffix `*<tag>`, because the layer's `NAME` field carries a sequence prefix like `(04) 17D-4-Q`). This QGIS Server build silently **ignores `CQL_FILTER`**, and WFS `TYPENAME` must be the **underscored** layer name (`Point_Aset_Plant_17`), not the display name. Returns `{found, lat, lng, name, layer}` JSON; a miss falls back to the layer-name search.

**QGIS 4 vs QGIS Server 3 format gotcha**: QGIS 4.x saves project custom properties in a nested form (`<properties name="properties">` container, `<properties name="WFSLayers">` children) that QGIS Server 3.x can't read (it wants the flat `<WFSLayers type="QStringList">` form) — WMS works (layers publish by default) but WFS GetCapabilities comes back with an **empty FeatureTypeList** and "TypeName could not be found", no matter how often the file is re-saved/touched/restarted (the journal logs "Loading a file that was saved with a newer version of qgis"). `deploy/qgis4-to-qgis3.py` (idempotent) rewrites the three WFS property blocks + container; run it after each QGIS-4 save **only if a project must be served by a 3.x server**.
